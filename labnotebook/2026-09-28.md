The CLI should be built as a stackl of thin layers: (i.) a point for command entry, (ii.) a parser (iii.) methods to hook into code that does the htings we care about. Let's create a design spec and begin to work through the details.

## CLI Design Spec Thoughts

Group based top level domains would be best. So we have several of these naturally: environemnts, experiments, models, agents, analysis, data. This will need to probably involve a table of some kind sopecifiying the groups, and API surfface for each group, then hooks from a modules file into each area under src/ 

Follow this with spec-driven dev, i.e. a short specification of what the feature does, what it reads and writes, how it behaves at the edges, and what it will not do, like what out spec limit is, very important... critical! for any agent based work. 

From the spec myself and an AI agent can derive an implementation plan (no code yet). This means the architecture, how the work splits into modules, the order to build things in (I like to have a commiits checklist of sorts), and the design decisions with their reasons.

Execution becomes task based and can be done in parallel with myself and agents, or in series for thorny or step dependant implementation. Each task gets its tests, gets run, and gets reviewed against the spec before the next one starts.
